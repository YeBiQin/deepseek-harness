DeepSeek Harness
不是一个程序，而是一套可组合的 Agent 底盘。

DeepSeek Harness（dsh）是一套以 Cordis 插件框架为基础的 Agent Harness：它把大模型、会话、工具、文件系统、Shell、权限、持久化和多种客户端入口拆成可以装配、替换、观察并安全清理的能力。

01 · DESIGN PRINCIPLES

四条主线，读懂整个系统

所有模块都可以回到这四条原则。它们决定了能力如何装入、如何协作、如何替换，以及什么信息必须留下可重建的记录。

✣

一切皆插件

LLM、Session、Tools、Agent Loop 等核心部件也通过插件组合。新行为优先接入既有扩展点，而不是把更多逻辑塞进中心循环。

可替换可装卸
⇄

服务 + 事件

Service 提供可主动调用的稳定能力；Event 提供观察、包装、拦截和策略扩展点。插件通过 Context 按 key 找能力。

⌘

配置是叠加补丁

Profile 组织 Bundle，Patch 按 id 覆盖或插入插件条目。运行时组合由配置层和依赖关系共同决定。

02 · ARCHITECTURE MAP

从命令到输出的一张总图

先看运行时关系，再看具体包名。外部入口只是窗口；真正共享的后厨是 Agent、Session、LLM、Tool Runtime 和能力 Provider。

启动层

dsh 解析模式，Profile 选择组合，Bundle 提供 Patch，Loader 将条目装入 Context。

核心运行层

Agent Loop 负责排队和推进 Turn；Session 负责记录事实；LLM 和 Tools 负责模型交互与实际动作。

适配与投影层

Web、Headless、ACP、SDK 负责输入翻译、生命周期等待和输出投影，不复制核心循环。

03 · BOOT & COMPOSITION

系统如何启动：配置先组合，能力后激活

dsh web 不是直接调用一个写死的 main()。它先构造最终 entry list，再让 Cordis 根据依赖激活插件。

1

CLI 选择运行模式

apps/cli/src/bin.ts 负责区分 profile、plugin、dump-config 等模式；它决定“想启动什么”，不直接创建 Agent。

2

Profile 找到 Bundle 和补丁

Profile 是具名运行组合，Bundle 是可分发的配置层。Web 和 Headless 是官方交付的运行模板，用户可在其上追加自己的 Patch。

3

Patch 应用到 entry list

典型顺序是：Bundle Patch → profile Patch → Harness Home Patch → 命令行 --patch。后应用层可按 id 覆盖前面的整条配置行，覆盖不是字段级深合并。

4

Loader 挂载到 Context

Loader 读取模块、配置和依赖，创建或使用 Cordis Context，等待 inject 声明的 Service 可用，再执行 apply(ctx, config) 或挂载 Service。

5

插件注册能力并拥有清理责任

插件在激活时注册 Service、Event、Tool、Adapter 或外部资源；这些注册必须属于插件的 Effect，卸载、配置替换或 HMR 时由 disposer 撤销。

查看实际组合结果
pnpm dsh --profile web --dump-config
pnpm dsh web --patch ./scratch-plugin/cordis.yml

Bundle 与 Profile 的区别

Bundle 回答“这个包贡献哪一层 Cordis Patch”；Profile 回答“本次启动按什么顺序组合哪些 Bundle”。

一个普通库如果只是被其他插件 import，不应声明成 dsh.bundle；只有配置层的分发包才需要成为 Bundle。

04 · CORDIS FOUNDATION

插件、Context、Service、Event、Effect

Cordis 是 Harness 的运行时地基。理解它的关键不是背 API，而是区分“主动调用”“运行时扩展”和“生命周期清理”。

P

Plugin

一个可加载、可卸载的功能单元。函数式插件通常导出 name、inject、Config 和 apply。

C

Context

当前作用域的共享工作台。它通过服务 key 暴露能力，也提供事件、注册和 Effect 方法；它不是随意堆放全局变量的对象。

S

Service

长期存在的直接调用能力，例如 ctx.llm、ctx.tools、ctx.sessions、ctx.agents。

E

Event

由运行时主动 dispatch 的扩展点，用于观察、包装、修改或阻止动作。事件的 dispatch mode 决定等待、顺序和返回值。

I

inject

插件对 Loader 的依赖声明，表示“这些 Service 就绪后我才能激活”。它不是 import 图，也不是手写的全局启动顺序表。

↺

Effect

把注册动作和清理动作绑定。监听器、工具、适配器、定时器和连接都应由创建它们的插件登记 disposer。

Dispatch mode等待与顺序返回值适合场景
emit同步，按注册顺序忽略广播“某个事实发生了”
parallel异步并行，等待全部完成无；错误聚合为 AggregateError多个独立观察者都必须完成
serial异步，按注册顺序，遇到首个 bail 值停止首个非 null/false/undefined 值多个候选处理者，第一个能处理的接管
bail同步，按注册顺序，遇到首个 bail 值停止首个 bail 值同步版候选处理
waterfall按注册顺序传递接力棒由 next() 传递并可包装请求/决策流水线，例如模型请求和工具执行

Waterfall 的硬规则：只观察、标注或包装的 listener 必须调用 next()；返回而不调用 next() 就是明确短路。审批拒绝、策略 deny 等有意接管的 listener 才应停止链路。

三个判断问题

我要主动调用稳定能力？
找 Service 方法。

我要参与某个运行时动作？
找对应 Event。

我注册了东西，谁来撤销？
使用 Effect 和 disposer。

一个 Turn 不是一次模型请求，而是一段从接收输入到暂时不再欠工作为止的工作周期；其中可以包含多个 Step 和多个工具调用。

Turn

从一组输入被接收，到 Agent 没有继续任务或被取消的工作周期。一个 Turn 可含零到多个 Step。

Step

一次模型请求及其关联的工具执行。模型得到工具结果后，Agent 可能在同一 Turn 中再次发起请求。

三种输入

关键扩展点：agent/pre-step 决定模型看到的输入；agent/request 包装模型请求；llm/stream 包装流式输出；tools/pre-execute、tools/execute、tools/post-execute 组成工具执行管线；agent/turn-stopping 参与轮次收尾。

实线箭头表示控制权向前推进；工具调用会在一个 Turn 内让 Agent 回到下一次 Step。

06 · SESSION & RECONSTRUCTION

Session 是事实账本，也是上下文重建源

Session 不只是聊天记录数组。它以追加式事件保存工作事实，再在每次模型请求前重新派生消息和请求元数据。

Session 的基本不变量

  • 事件追加写入，序号连续，事件数据是可持久化 JSON。
  • 事件快照和日志不会被调用方事后改写。
  • 模型可见内容必须可从日志重建。
  • 持久化后端（如 JSONL、SQLite）保存事实，但不替代 Session 的事件语义。

Surface 与 deriveMessages()

Surface 是账本中当前对模型可见的消息页。deriveMessages() 根据事件和 Surface 规则重新算出模型历史，而不是维护一份可能与日志分叉的隐形数组。

因此，同一套事实可以支持模型请求、UI 回放、恢复、Fork、持久化和 Snapshot。

事件 / 信息性质作用
turn/start、turn/end持久事实表示一轮工作周期的开闭和结果边界。
step/start、step/end持久事实表示模型请求与工具执行步骤的边界。
user/message持久事实 / 可成为 Surface用户输入或替换后的摘要节点。
assistant/chunk、assistant/message持久事实前者保留流式过程，后者保存组装完成的稳定消息。
tool/call、tool/result持久事实保存工具调用及结果，支持回放和下一步上下文。
request/header、request/context请求元数据保存模型、系统提示、工具 Schema、路由和容量等配置；它们不是聊天历史。
agent/status、tools/pre-execute实时扩展参与当前控制或通知，但不能自动替代需要恢复的持久事实。

Replay / Restore

从日志恢复 Session 和模型上下文，不依赖某个入口内存中的临时状态。

Fork

从日志边界复制工作账本。可继承完整、平衡且以完成 Turn 结尾的历史前缀。

Flush

把内存中已追加的事实提交到持久化后端；“Agent idle”和“Session flush”是两个不同的等待点。

Session 的三段式重建

同一批持久事实经过 Surface 选择后，成为模型下一次请求的消息；实时通知不等于持久化事实。

工具的完整闭环

最小 defineTool 思路
export const inject = ['tools']

export function apply(ctx) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: { type: 'string', required: true }
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [
        { type: 'text', text: value }
      ]
    },
    async execute(args) {
      return "Hello, " + args.name + "!"
    }
  }))
}

四条工具通道

  1. 模型可见：name、description、parameters 进入 Prompt。
  2. 程序可见：execute() 返回符合 output.schema 的规范 JSON 值。
  3. 模型结果：output.render() 把规范值转成模型内容。
  4. UI 投影：presentCall、presentResult、presentationMeta 生成卡片、Terminal 或 Diff。

展示方法必须是纯函数：不要读文件、读 Session、看时间或生成随机 ID，否则实时显示和回放会不一致。

工具策略流水线：tools/pre-execute 负责允许、拒绝或询问；tools/execute 围绕实际执行包装超时、重试或指标；tools/post-execute 处理结果或增加上下文；tools/result 只观察已冻结的最终结果。最终不可撤销的禁止条件适合 ctx.tools.guard()。

工具调用的八个落点

每个落点的职责不同：决定是否继续、执行动作、整理结果和写回 Session 不能混在同一个 execute 函数里。

并发：默认 fail-closed

只有 isConcurrencySafe(args) 精确返回 true 才能标为 parallel；缺省、其他 truthy 值或异常都按 exclusive 处理。

作用域：可见性必须一致

restrict() 同时影响模型 Schema 可见性和执行解析。不能只把工具从 Prompt 隐藏，却让过期或直接 Tool Call 仍然执行。

08 · SAFETY & CONTROL

权限、审批与沙箱是两套旋钮

审批回答“这一次操作能不能继续”；沙箱回答“进程对文件系统能产生什么效果”。它们可以组合，但由不同的服务和事件负责。

一次审批请求

A

asked

工具/策略层构造精确的 ApprovalRequest，写入 approval/asked 审计事实。

B

decide

ask 走 approval/request waterfall；never 在 waterfall 之前直接拒绝。

C

closed result

合法结果是 allowed-once、rejected、cancelled、unavailable；只有第一种允许当前一次调用继续。

Fail-closed：没有应答者、应答者出错、请求取消或结果非法，都不能默认为 allow。审批审计事件也不进入模型 transcript。

三种沙箱模式

模式文件效果执行逻辑
read-only拒绝写入通过沙箱后端约束 argv
workspace-write允许工作区根及后端承诺的临时区域解析绝对 workspaceRoot 后 confine
danger-full-access绕过隔离，运行原始 argvConsumer 显式分支，不是假装传一个无限制 policy

Provider 还要报告 enforcement：full 表示完成承诺，partial 只管控部分效果。Consumer 必须区分普通命令失败、sandbox denial 和 runner failure。

Permission Presets：一个选择器，两个强制执行旋钮

预设服务把 sandbox/mode 和 approval/policy 组合成客户端可选项。默认示例包括 workspace-write + ask 与 danger-full-access + never。

custom 不是预设表里的目标，而是当实际两个旋钮无法匹配声明项时派生出的显示状态。切换时先写 permission/preset，再由各自 setter 写入真正发生变化的 sandbox/approval 事件；重复选择当前生效值不追加多余日志。

可交互示意：分别调整两个旋钮

改变任一旋钮只改变对应的运行时策略；预设名称是对两个有效值的组合投影。

09 · ADVANCED RUNTIME

从长任务到多 Agent 的高级能力

高级专题都遵循同一套原则：明确拥有者、记录可恢复事实、区分 live handle 与 snapshot，并在取消和 dispose 路径上完成资源结算。

J

Background Jobs

Job Registry 管理品牌化 JobId、状态、授权、快照、等待者和完成通知；生产方拥有进程、子 Agent 和输出缓冲等实际资源。

  • 状态经过 running → stopping → completed/killed/failed。
  • 授权依据 owner 的 SessionId，不依赖可预测 id 的保密。
  • 流式输出通过唯一游标读取增量；最终输出型任务在完成后重复读取不消费。
  • done 必须等生产方释放资源后才结算。
A

Subagents

一次性委派和可继续 child 是两种不同的生命周期，不应包成同一个永不结束的 Promise。

  • One-shot 使用 SubagentRun，等待 result 后调用 dispose()。
  • Continuable child 是持久 Session，最多一个 live Activation，输入进入唯一 FIFO inbox。
  • 能力、委派深度、tool filter、persona 和 output schema 在启动期检查。
  • Fork 只表示继承历史 seed，不代表继承工具、权限、服务或文件权限。
W

Workflow

Workflow 是在 worker 中运行的受控脚本编排引擎，不是另一套 Agent Loop。

  • meta、args 和脚本文本职责分离，meta 在脚本运行前校验。
  • phase() 只提供阶段标题，不自动产生并发或流水线语义。
  • 配置错误、取消、child 无法启动和超出上限属于 fatal error。
  • result 不 reject；dispose() 仍必须等待有界的 worker 和 child 清理。
C

Compaction

压缩通过替换 Surface 缩短上下文，不直接截断事件数组。

  • 日志事件按 start → summary → replacement user/message → end 记录操作与锁。
  • compaction/* 事件不直接进入模型 transcript，真正改变 Surface 的是 replacement 消息。
  • 范围必须在工具 call/result 配对边界上平衡。
  • 失败、取消和持久化故障要分类记录；单个不可拆分的大请求不能靠压缩修复。
P

Agent Presets

Preset 让不同会话在同一进程拥有不同的工具、提示词和投影，同时共享宿主级 Registry。

  • 常驻 roster 挂载 preset scope，agent scope 通过父链加入。
  • Preset 文件变化形成新代际；已有会话继续使用旧代际，保护模型前缀稳定性。
  • 选择写入 agent-preset/selected，恢复不能只依赖 Session header。
  • trust 主要用于展示和创作权限，不把不可信 preset 自动变成沙箱。
T

Agent Teams（实验性）

Team Lead、具名 teammate、持久 mailbox 和共享任务 DAG 建立在 continuable child 之上，当前有明确限制。

  • TeamId 等于 Root SessionId；成员名字在 Team 生命周期内不可复用。
  • Lead 先持久化 queued，target 侧去重后再记录 delivered。
  • 任务更新使用 expectedRevision，blockedBy 必须无环。
  • 共享 cwd，不提供 worktree、自动 merge、文件锁或跨进程 exactly-once。
实验性需显式启用
10 · MULTI-ENTRY OUTPUT

四个窗口，共享一间后厨

不同入口的差异集中在输入格式、等待方式、输出协议和退出生命周期；它们不应重复实现 Agent Loop、工具策略和 Session 追加规则。

入口阅读四问：输入从哪里来？谁创建 Agent？过程在哪里完成？外部究竟看到了什么？沿着“输入 → Agent → Session → 输出”四个节点阅读，比从 UI 组件或协议细节开始更容易保持全局。

配置的两重职责

TypeScript 接口提供编译期类型；Schemastery schema提供运行时校验和默认值。二者共同让错误配置尽早失败。

配置修改会触发旧插件实例卸载并执行 Effect 清理，再用新配置重新激活。不要把注册或资源放在脱离插件生命周期的全局状态中。

常见误区速查

  • 把 import 当成运行时挂载。
  • 把 inject 当成启动顺序数组。
  • 把 Event 当成没有 dispatch 语义的普通回调。
  • 只写注册不写 Effect 清理。
  • 在 Consumer 里直接 import Provider。
  • 把 UI 格式、自然语言话术当成工具规范值。
  • 把 unavailable 当成隐式 allow 或自动重试。
  • 把实验性 Agent Teams 当成稳定的普通子 Agent。

13 · GLOSSARY

核心术语表

这些词在源码、配置、测试和知识材料中反复出现。先掌握它们的职责边界，再进入具体实现。

术语含义不要混淆成
Harness围绕 LLM 构建长期运行 Agent 的装配、执行、记录和入口系统。单次 LLM API 调用。
Plugin可加载、可卸载并拥有生命周期的功能单元。只被 import 的模块。
Context当前作用域中解析 Service、注册 Event 和管理 Effect 的运行时工作台。无边界的全局变量容器。
Profile用户要启动的一套具名插件组合。单个可分发 Bundle。
Bundle贡献一层 Cordis Patch 的可分发包。只作为普通 import 库的依赖。
Patch / Overlay按插件 id 插入或替换配置条目的层。字段级深合并配置。
Service可被其他插件主动调用的稳定能力。只用于通知的 Event。
Effect安装与清理绑定在同一插件生命周期中的可逆副作用。没有 disposer 的全局注册。
Turn / StepTurn 是完整工作周期；Step 是一次模型请求及其工具执行。一条用户消息必然对应一次请求。
Session Log追加式、可持久化、可重建的事件账本。仅供 UI 使用的聊天数组。
Surface从 Session 事件投影出的当前模型可见消息位置。简单的连续 seq 区间。
Provider / ConsumerProvider 实现抽象能力；Consumer 使用能力产生产品行为。Consumer 直接绑定 Provider 内部实现。
Approval针对一次具体操作的 allow/reject/cancel/unavailable 决定。永久权限或沙箱模式。
Sandbox限制进程文件效果的执行策略和后端。自动等价于网络隔离。
Preset按会话组合工具、提示词和投影的配置目录。一种新的 Agent Loop。
